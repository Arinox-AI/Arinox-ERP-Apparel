# Fixes · 9 November 2026

Two reports from the user, both reproduced against the live ERP before anything was changed.

---

## 1 · "I cannot create a Sales Order through the tower" (and the steps after it)

### What was happening

Reproduced on deal **#3 (C9043 order inquiry)**, which was signed and ready to order:

```
deals.DealError: Sales Order not saved: Row #1: Quantity for Item APPAREL-STYLE cannot be zero.
```

The contract the tower had made looked like this:

| size | XXS | XS | S | M | L | XL | XXL |
|---|---|---|---|---|---|---|---|
| qty | **0** | 201 | 198 | 200 | 200 | 200 | **0** |

That is a normal contract: the buyer lists a size range and orders nothing in two of the sizes. But the ERP's
`arinox_sales_contract_make_sales_order` script turned **every** size row into a Sales Order line, and Frappe refuses a
whole document that contains a zero quantity. So no Sales Order could be made from any contract with a size at 0 —
in the tower **or** from the ERP's own button on the Sales Contract.

### The fix (two halves, on purpose)

* **The tower never sends an empty line** — `deals.make_order` drops every row whose quantity is 0 or blank before the
  insert, whatever the ERP's script returns, and writes on the deal's timeline which sizes were left off
  (`Sizes with no pieces are not on the Sales Order: XXS (Cool Capri Wash), XXL (Cool Capri Wash).`). If *every* size is
  zero the person gets a sentence, not a Frappe exception.
* **The ERP's own script is fixed too** — `arinox_sales_contract_api_make_order` skips `cint(s.qty) <= 0` and throws a
  readable error when nothing is left. Changed in the live site (Server Script
  `arinox_sales_contract_api_make_order`), in the tower's vendored copy, and in the upstream bundle
  (`apparel-modules/v2/hosted_bundle/17_server_scripts.json`) so a re-vendor cannot bring the bug back.

Two halves because either one alone is fragile: the tower must be right even about a script somebody reverts, and a
person working in the ERP desk must get the same order.

### Verified end to end against the live ERP

`deals.make_order` on a copy of the live database, deal 3, contract `CTXGVN26.11.008`:

```
Sales Order SAL-ORD-2026-00084   docstatus 0 (draft)   grand_total 10,419.57
rows: XS 201 · S 198 · M 200 · L 200 · XL 200   @ 10.43 each   (XXS / XXL dropped, said so on the timeline)
```

The test Sales Order was then deleted again, so the deal is exactly as the user left it and pressing
**Make the Sales Order** produces the order as the first attempt.

Nothing else after the order was broken: `deal_track` (Ship & track) and `deal_dashboard` answer normally on the same
copy with the order in place.

## 2 · "Take me to the ERP takes me to the main page, not the intended page"

### What was happening

Every address the product handed out was built in one of two places, and the buttons in the deal page all used
`erp.base_url` — which is `<site>/desk`, the ERP **front page**. So "Open the ERP" on a deal opened the ERP home while
the deal's own Sales Order page was right there.

### The fix — one builder, one resolver, no literals

**`backend/erp.py` is now the only place that knows how an ERP address is spelled:**

| function | what it answers |
|---|---|
| `doctype_slug(doctype)` | the route segment the desk router uses — `Sales Order` → `sales-order` |
| `desk_prefix()` | where *this* site keeps its desk: asks the site once (a newer install answers `/desk`, an older one only `/app`), remembers it |
| `doc_url(doctype, name)` | the page of one document |
| `list_url(doctype)` | the DocType's list page — where to send someone while the document does not exist |
| `url_for(doctype, name)` | the one entry point: document page, else list page, else the desk |
| `desk_url()` | the front page (last resort) |

`functions._erp_links` (the legacy Actions / Risks / Inbox buttons) now calls the same builder instead of assembling
`/desk/<slug>` itself. That was the "do not hard-code the url everywhere" point: there is now exactly one
implementation, and it derives the route from the site rather than from a literal typed in a screen.

**`deals.erp_status` now resolves which page each step is about** (it already read every document, so this is free):

```
by_step = {
  "inquiry":  Opportunity CRM-OPP-2026-00004,
  "costing":  Cost Sheet CS-2026-00002,
  "quote":    Quotation SAL-QTN-2026-00003,
  "contract": Sales Contract CTXGVN26.11.008,
  "order":    Sales Order SAL-ORD-2026-00084,      ← or "Open the sales order list" before it exists
  "track":    Sales Order SAL-ORD-2026-00084,
}
focus = by_step[<the step the deal is on>]        ← what the side panel button opens
```

Each entry carries `doctype`, `name`, `url` and a ready-made button label. The deal page reads them
(`erpPage(erp, step)` in `app/DealPage.tsx`) and never assembles a path itself:

* the Inquiry card's button opens the Opportunity,
* the Costing card's button opens the Cost Sheet,
* the "In the ERP" panel opens the document of the step the deal is on (Sales Order once ordered, contract before),
* and when a document does not exist yet the button opens that DocType's **list** ("Open the sales order list"),
  never the ERP front page.

Every step key is the same string the deal page's `STEPS` array uses, so a step and its page cannot drift apart.

Also fixed while checking the built page in a browser: on a phone the card header crushed its title into a column and
pushed the ERP buttons off the card (`theme.css`, 760 px breakpoint — the actions now drop under the title).

### Verified

* Playwright against the built `index.html`, real backend, copy of the live data: contract step → contract page,
  Inquiry → Opportunity, Costing → Cost Sheet, Sales order → the order; **no button anywhere points at `/desk`**;
  no console errors at 1440 px or 390 px; screenshots at `/tmp/deal_order.png` and `/tmp/deal_order_mobile.png`.
* `backend/tests/test_erp_links.py` — **47 assertions**: the builder (slug, escaping, list vs document, a site without
  `/desk`, an unreachable site), `functions._erp_links` agreeing with it, `by_step` / `focus` per step and the list
  fallback, the empty-size Sales Order, the same order with the **old** script put back into the registry, and the
  shipped script carrying the guard.
* Whole suite re-run: deals 128, pipeline guard 106, contract amend 29, ship & track 75, costing 80, tsr core 96 —
  green. (`test_chain`, `test_wip_edges`, `test_wip_plan` fail on this machine for the reason they failed before:
  they want live production data / the pack builder, which this deployment does not hold.)
